# Requirements

## Intent Analysis

- **User Request**: Three feature requests for the admin panel of EcoSistema (Gestão de Obras): (1) a client-scoped filter/cash-closing view on the "Obras" tab, suggested by a colleague and relayed by the product owner; (2) color-coding (red/blue/green) for financial figures; (3) a notification system covering obra status/movement — clarified through Q&A to mean real push notifications (Firebase Cloud Messaging), in both directions (admin↔cliente).
- **Request Type**: New Feature (all three items add net-new functionality; none are bug fixes, though implementing push notifications properly also touches the "orphaned manifest.json" finding from the reverse-engineering pass).
- **Initial Scope Estimate**: Multiple Components — `admin/index.html`, `admin/app.js`, `cliente/app.js`, `cliente/index.html`, `js/data.js`, `js/firebase-config.js`, `css/style.css`, `firestore.rules`, `manifest.json`, plus a **new** server-side component (Firebase Cloud Functions) that does not exist in the current codebase.
- **Initial Complexity Estimate**: Moderate to Complex. The client-filter and color-coding features are Moderate (UI + aggregation logic on existing data). The push-notification feature is Complex: it introduces the project's **first backend/server component**, a service worker, a device-token data model, and new Firestore security rules — all previously absent from this 100%-client-side architecture.
- **Depth Applied**: Standard (per depth-levels.md) — normal complexity, clarification was needed and has been resolved; not "Comprehensive" since this isn't a full system migration or a high-risk regulated domain.

## Functional Requirements

### FR-1 — Filtro de cliente na aba "Obras" (visão "Fechamento de Caixa")
- **FR-1.1**: Add a client-selector dropdown at the top of the existing admin "Obras" tab (no new tab/page — Q1=A).
- **FR-1.2**: Selecting a client filters the obras list to only that client's obras currently in `status:'andamento'` (in execution), and shows a financial summary for the selected period: total **entrada**, total **repasse**, total **sobra** (Q2=B) — this is the "fechamento de caixa" the user described.
- **FR-1.3**: Include a fixed "Sem cliente / Outros" option in the dropdown that groups all obras where `clienteId` is empty/null (Q3=A) — no change to the requirement that an obra may exist without a linked client.
- **FR-1.4**: The dropdown must be populated from the existing `usuarios` (tipo:'cliente') collection, consistent with how client selects are already populated elsewhere in `admin/app.js` (`popularSelectClientes`).

### FR-2 — Cores para valores financeiros (repasse / entrada / sobra)
- **FR-2.1**: Apply a consistent color mapping wherever repasse/entrada/sobra values are displayed: **repasse = red**, **entrada = blue**, **sobra = green** (Q4=A).
- **FR-2.2**: **Sobra** (net profit) is computed as `valorTotal − repasse` — **[CORRECTED 2026-07-06 during Build and Test]** originally specified here as `entrada − repasse`; the product owner clarified during manual testing that `entrada` (the down-payment actually received) must NOT drive the profit figure — profit is based on the obra's total contracted value (sum of `val` across its etapas) regardless of how much has been paid in so far. `entrada` remains a separate, independent cash-flow indicator (its own tile, per FR-2.3), decoupled from Sobra. Computed per obra and, in the Fechamento de Caixa view (FR-1.2), aggregated across all filtered obras.
- **FR-2.3**: Apply the coloring in two places: the existing obra detail screen (admin) where these values already render, and the new Fechamento de Caixa view from FR-1 (Q6=B). Reuse/extend the existing CSS design tokens (`--bg-danger`/`--text-danger` for red, `--bg-success`/`--text-success` for green); a new "info/blue" token pair should be added to `css/style.css` for entrada, following the same custom-property pattern already used for the other badge colors.

### FR-3 — Sistema de notificações (push + cobertura de eventos + ambas as direções)
- **FR-3.1**: Notifications must be delivered as real OS/browser push notifications via Firebase Cloud Messaging (FCM), visible even when the app is closed/minimized, requiring the user to grant browser notification permission (Q7=B).
- **FR-3.2**: Admins must also receive notifications for client-initiated actions — not just clients receiving admin-initiated ones as today (Q8=A). Concretely: a client submitting a solicitação, a client approving/rejecting an orçamento, a client registering a payment, and a client rating a completed obra must all notify the relevant admin(s).
- **FR-3.3**: Extend the notification-triggering event set beyond the current list (obra_criada, obra_concluida, etapa_iniciada, etapa_concluida, diaria_registrada, orcamento_enviado) to also include: cobrança enviada (admin→cliente), resposta do cliente à cobrança — pago/contestado (cliente→admin), and decisão do cliente sobre orçamento — aprovado/rejeitado (cliente→admin) (Q9=B).
- **FR-3.4**: Because a client-side script cannot push a notification to another user's device directly (this requires the FCM Admin SDK with elevated credentials), this requires a new server-side component — Firebase Cloud Functions — triggered on relevant Firestore writes (e.g. `onCreate` of a `notificacoes` document, or directly inside dedicated callable/triggered functions for each event in FR-3.3), which looks up the recipient's stored FCM device token(s) and sends the push.
- **FR-3.5**: The existing in-app `notificacoes` collection/feed continues to serve as the underlying event log and the in-app notification history (what the user sees when they tap into the app after receiving a push, and what populates the notification list/badge count already present in both panels).
- **FR-3.6**: A new `usuarios/{uid}.fcmTokens` (or a `fcm_tokens` subcollection, to be decided at Application Design) must store each user's registered device token(s) so Cloud Functions know where to send. Token registration happens client-side after the user grants notification permission.
- **FR-3.7**: A service worker must be added to handle background push receipt (required by the Web Push/FCM spec for notifications while the tab isn't focused) — this also gives the opportunity to fix the currently-orphaned `manifest.json` (not linked from any HTML file, empty `icons`) found during reverse engineering, since a working PWA install experience and a working push feature are normally delivered together.

## Non-Functional Requirements

### Security (Security Baseline extension — **Enabled**, full enforcement, per Q10=A)
- The introduction of Firebase Cloud Functions (FR-3.4) is the project's first server-side component and the first place several SECURITY-baseline rules become concretely applicable — most notably **SECURITY-08 (Application-Level Access Control)**: every Cloud Function must independently re-verify the caller's role/ownership server-side rather than trusting client-supplied data, closing the same class of gap the reverse-engineering pass flagged as Critical in the current pure-client-SDK architecture (self-promotion to admin, cross-tenant `etapas` read).
- **Recommendation (not yet in scope unless confirmed)**: because standing up Cloud Functions for push notifications creates the natural place to also enforce authorization server-side, consider folding the reverse-engineering's Critical findings — #1 (admin self-promotion via unrestricted `usuarios` self-write) and #2 (cross-tenant `etapas` read leak) — into the same unit of work during Workflow Planning, rather than as a separate later effort. This is a recommendation to confirm at the next approval gate, not an assumed requirement.
- Rules **SECURITY-01, 02, 04, 07** (encryption/TLS, load-balancer/CDN access logging, HTTP security headers, VPC/network ACLs) are **N/A** for this architecture — there is no self-managed network layer, load balancer, or CDN; Firebase manages TLS termination and Netlify serves the static assets. This should be re-confirmed, not silently assumed, once Application Design/Infrastructure Design for the Cloud Functions unit is done.
- Rules **SECURITY-03 (Application-Level Logging), SECURITY-06 (Least-Privilege IAM), SECURITY-09 (Hardening), SECURITY-12 (Auth/Credential Mgmt — delegated to Firebase Auth, but MFA-for-admins and session invalidation should be reviewed), SECURITY-14 (Alerting), SECURITY-15 (Exception Handling/Fail-Safe Defaults)** become applicable to the new Cloud Functions unit and must be addressed during NFR Requirements/NFR Design for that unit.
- Rule **SECURITY-13 (Integrity)**: the existing CDN-loaded Firebase SDK and Tabler Icons webfont `<script>`/`<link>` tags have no Subresource Integrity (SRI) hashes today — flagged for remediation, applicable regardless of the new features.

### Testing (Property-Based Testing extension — **Enabled**, full enforcement, per Q11=A)
- No test framework exists in the repository today (confirmed in reverse-engineering/code-quality-assessment.md) — a PBT framework (recommendation: **fast-check**, per property-based-testing.md's JS/TS row) must be selected and configured as part of this work, at minimum for the new Cloud Functions unit and for any pure calculation logic introduced by FR-2 (`sobra = entrada − repasse`, and the Fechamento de Caixa aggregation across multiple obras/etapas — both are strong PBT-03 invariant-testing candidates: "aggregated total across obras equals the sum of per-obra sobras", "sobra never miscomputes when repasse exceeds entrada", etc.).
- FR-3's notification-triggering logic (event → notification document → push) is a good PBT-06 candidate (stateful: notification read/unread state transitions) once implemented.
- Rules PBT-01 through PBT-10 will be carried forward and evaluated concretely during Functional Design and Code Generation for whichever unit(s) implement FR-2's calculations and FR-3's Cloud Functions.

### Performance
- The Fechamento de Caixa aggregation (FR-1.2) must not reintroduce or worsen the listener-churn pattern already flagged in reverse-engineering/code-quality-assessment.md (finding #12, `escutarTodasEtapas` full teardown/rebuild) — the per-client aggregation should be computed from data already held in memory (`db_obras`/`window._todasEtapas`) rather than opening new per-filter Firestore listeners.

### Usability / Accessibility
- The notification permission prompt (FR-3.1) must clearly explain why permission is being requested (Brazilian Portuguese, consistent with the rest of the UI's language) and must not block app usage if the user declines — the existing in-app notification feed (FR-3.5) remains the fallback for users who deny push permission.

### FR-4 — Avaliação por Critérios do Serviço, vinculada ao Parceiro Executor (Unit 3 candidate)
- **FR-4.1**: O cliente avalia a **obra** como um todo, uma única vez, quando ela é concluída — mesmo gatilho/evento (`obra_concluida`) já usado hoje (Q1=B, Q7=A). A avaliação por critério individual (não por etapa) foi escolhida em vez de avaliar cada etapa separadamente.
- **FR-4.2**: A avaliação é composta por 3 critérios fixos, cada um de 1 a 5 estrelas, sem opção de edição/configuração pelo admin (Q3=A): **Tempo de execução**, **Acabamento**, **Organização e limpeza**.
- **FR-4.3**: A "Avaliação Geral" é calculada automaticamente como a média simples dos 3 critérios daquele envio (Q4=A). A UI (tanto o resumo do cliente quanto a tela de detalhe do parceiro no admin) deve exibir a nota de cada critério individualmente, além da média geral — não apenas a média (esclarecimento do usuário na Q4).
- **FR-4.4**: Este novo sistema **substitui** completamente a avaliação simples de nota única que existe hoje na obra (`avaliacaoNota`/`avaliacaoComentario`/`avaliadoEm`) (Q6=A). Isso implica remover/alterar:
  - `firestore.rules` — bloco `match /obras/{obraId}` `allow update` (hoje restrito a `hasOnly(['avaliacaoNota', 'avaliacaoComentario', 'avaliadoEm'])`) passa a permitir os novos campos de critérios em vez desses três.
  - `cliente/app.js` — `abrirAvaliacao`, `renderEstrelasAvaliacao`, `selecionarEstrela`, `enviarAvaliacaoObra` (hoje um único conjunto de estrelas; passam a ser 3 conjuntos, um por critério).
  - `js/data.js` — `enviarAvaliacao` (assinatura muda para aceitar os 3 critérios).
  - Um campo de comentário livre é mantido (equivalente ao `avaliacaoComentario` atual) — não foi solicitada sua remoção.
- **FR-4.5**: Envio único e travado — sem edição posterior, mesmo comportamento de hoje (gate via `!obra.avaliacaoNota`, adaptado para o novo campo) (Q8=A).
- **FR-4.6**: A avaliação é vinculada a **todos os parceiros distintos** presentes em qualquer etapa **concluída** daquela obra (via `etapa.parceiroId` ou `etapa.parceiros[].parceiroId` — mesmo critério de filtro (`status === 'concluido'`) já usado em `renderParceiroDetalhe`). Se houver mais de um parceiro distinto, cada um recebe a nota (os 3 critérios + a Geral) integralmente no seu histórico — não há divisão/rateio por valor de repasse (Q2=A).
  - **[Assunção a confirmar em Functional Design]**: "parceiro vinculado à obra" usa o mesmo filtro `status === 'concluido'` já existente no código para consistência com o histórico financeiro do parceiro; não foi perguntado explicitamente se etapas *não concluídas* também deveriam contar (assumido que não, por analogia).
- **FR-4.7**: A nota acumulada de cada parceiro é a **média aritmética** (não soma) de cada critério — e da Geral — entre todas as avaliações já recebidas por ele, recalculada a cada novo envio (Q5=A).
  - **[Decisão de arquitetura sugerida, a confirmar em Functional Design]**: seguindo o padrão já estabelecido no projeto (Performance NFR abaixo, e a forma como `renderParceiroDetalhe` já calcula `historico`/`totalDevido` em memória a partir de `db_obras`/`window._todasEtapas`), a média acumulada do parceiro deve ser **computada em tempo real a partir das obras avaliadas já existentes**, e não mantida como um contador incremental no documento do parceiro — evita inconsistência e não exige nova Cloud Function.
- **FR-4.8**: A nota acumulada do parceiro (por critério + Geral, no formato do exemplo do usuário: "Benedito: Acabamento 5/5, Execução 5/5, Organização e limpeza 5/5, Avaliação Geral: 5/5") aparece **apenas** na tela de detalhe do parceiro no admin (`renderParceiroDetalhe`) — não na listagem geral de parceiros (Q9=A).
- **FR-4.9**: O cliente passa a ver o **nome do parceiro** que executou o serviço no momento de enviar a avaliação — mudança em relação ao comportamento atual, em que parceiros são informação puramente interna/admin (Q10=B).
  - **Implicação de segurança a resolver em Functional Design/NFR**: hoje o cliente não tem permissão de leitura sobre a coleção `parceiros` (`firestore.rules` — `match /parceiros/{parceiroId}` é restrito a `logado()`, mas os dados sensíveis do parceiro — CPF/CNPJ, telefone, repasses — não devem ser expostos ao cliente). A opção mais provável é desnormalizar apenas o **nome** do parceiro na etapa/obra (já existe precedente: `parceiroNome` já aparece em alguns pontos do código de admin), em vez de liberar leitura da coleção `parceiros` inteira ao cliente.

## Summary of Key Requirements

1. Client filter + period financial summary ("Fechamento de Caixa") added to the existing admin Obras tab, including an "Outros/Sem cliente" bucket.
2. Consistent red/blue/green color coding for repasse/entrada/sobra, applied on the obra detail screen and the new Fechamento de Caixa view; `sobra = entrada − repasse`.
3. Real push notifications (FCM) covering an expanded event set, flowing in both directions (admin↔cliente) — requiring the project's first server-side component (Firebase Cloud Functions), a device-token data model, and a service worker; the existing in-app notification feed is retained as the underlying log/fallback.
4. Security Baseline and Property-Based Testing extensions are both enabled with full enforcement for this and future units of work; several Security Baseline rules only become concretely actionable once the new Cloud Functions unit exists, and a recommendation to also close the two Critical RE security findings in that same unit is flagged for confirmation.
5. **(New — Unit 3 candidate)** Client-submitted obra rating evolves from a single 1-5 star field into 3 fixed criteria (Tempo de execução, Acabamento, Organização e limpeza) plus an auto-computed overall average, replacing the old field entirely; the rating accumulates (as a running average, computed on read, not stored incrementally) against every distinct parceiro linked to the obra's completed etapas, displayed only on that parceiro's admin detail screen; the client will now see the parceiro's name when rating, which requires a small, deliberate data-exposure change (name-only, not full parceiro record).
